# Website enquiry intake

The public Academy contact form posts to `POST /api/contact/enquiries`. Requests are stored in the existing South Africa North Cosmos LMS container, in the home organisation partition and a separate `contact-enquiries-v1` collection. No email notification or acknowledgement is sent. Staff must monitor the inbox at `https://portal.skunkworksacademy.com/?inbox=contact` and reply using their approved team mailbox.

The inbox uses existing Microsoft sign-in and `requireAdmin`, which checks the home tenant and `Portal.Staff`/`Portal.Admin` roles. The API exposes no anonymous read, search or list operation. Staff records and errors use `Cache-Control: no-store`. The browser never receives storage credentials. Neither request bodies nor contact addresses are written to application logs.

The only public receipt contains a random UUID. The server normalises and validates the name, reply email, allowed topic and message, rejects the honeypot, limits payload size, and allows only the two Academy website origins (plus the portal). Durable optimistic counters cap intake at 200 requests per hour overall and five per normalised reply address. These are abuse limits, not identity verification; CORS and email addresses are not authentication. No IP address is retained. If abuse warrants stronger controls, add a verified challenge before increasing limits.

The UUID and a SHA-256 digest make retries idempotent. A create-only database write is followed by a point read; success is returned only after the saved digest matches. Storage failure never falls back to memory. Enquiries explicitly disable automatic container expiry (`ttl: -1`); staff apply the existing privacy/retention policy and authorised deletion via normal database administration. Rate counters contain only time buckets, counts and hashed addresses. Topic filters route training, learner support, business, editorial, privacy, legal and general enquiries within the staff inbox; they do not send messages to departmental email addresses.

`infra/portal-api.bicep` adds the apex and www contact origins to existing CORS settings. The deployment workflow restores the previously tested guarded Skunkie activation step from successful release `30b710a`; this step was missing on main even though the workflow still paused Skunkie. The model, allowance and activation checks are unchanged.

Validation: `npm test`, `npm run build:api`, `npm run build`. Contact tests cover create/readback, retry, conflicting references, invalid inputs, storage failure, throttling, preflight and denied staff reads. Use only clearly synthetic `example.invalid` data for production smoke tests, marked “no response needed”. A receipt proves database readback, not a staff response or mailbox delivery.
